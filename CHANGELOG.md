# forge

## 1.0.0

### Major Changes

- 13e4dc9: Add the clean-code skill with references for naming, functions, control flow, classes and formatting, and guides for Swift, Kotlin, Java, TypeScript and Python. Each guide names the standard formatter and linter of its language, oxfmt and oxlint for TypeScript, swift-format for Swift, ktlint for Kotlin, google-java-format with Checkstyle for Java and Ruff for Python, with a configuration to copy under `formatting/<language>/`. The linters hold three rules for reading speed where the language allows, at most four parameters, no nested ternary and no else after a return. The steps point to the principles laziness-protocol, minimize-reader-load, model-the-domain, boundary-discipline, type-system-discipline and test-behavior-not-implementation, and the TypeScript guide points to typescript-best-practices.
- cc504b9: Add the code-comments skill with a guide per language and a PostToolUse hook that checks every written comment for long dashes, semicolons, length and unlinked TODOs. A comment links the plain-text form of a documentation page, `.md` on docs.github.com and code.claude.com, `.patch` on a commit URL and raw.githubusercontent.com for a file, so an agent that follows the link reads Markdown instead of HTML.
- 58204a5: Add the commit skill. It sets up commitlint and husky from the official guides, installs the upstream conventional-commit-message and committing-with-commitlint skills globally, finds the GitHub issue for the footer and splits the stage by topic. Every message is written in English, with a body per technical-writing. A calling skill can state that the work has no issue.
- 90d41a3: Add the diagrams skill for Mermaid diagrams of flows and structures, with one question per diagram, the type picked by that question and a table that links each element to its source. A diagram goes in `docs/` or in the README of the folder that holds the code, and a planned state marks what a change adds, changes and removes. A PostToolUse hook parses every mermaid block with the Mermaid of the project and names the diagrams whose table links an edited file. Mermaid stays pinned to the oldest version that GitHub, VS Code and JetBrains render.
- 62e8242: Add the engineering skill and the engineer agent. `/engineering` works every task through the playbook that matches it, Feature, Bug fix, Refactoring, Investigation, Perf issue, Hillclimb, Runtime forensics, Trace forensics, Prototype, Visual parity, Authoring a skill, Eval, Autonomous run, Session pickup, Worktree cleanup and Opening a PR, with the non-negotiables, the principles index and the autonomy, subagent and reply rules of pstack. `/engineering #<issue>` routes to the Ticket playbook, which works a GitHub issue to a pull request in its own worktree `../<repo>-<number>`. It grills only a criterion that reads two ways, a contradiction or a choice the user would see, settles a technical fork through the Prototype playbook, opens the playbook the label names, implements independent criteria in parallel through the engineer agent and commits criterion by criterion. interrogate reviews the diff with a second model family, blast-radius runs when the diff changes a schema, a public API, the dependencies or a flag, and a stuck test goes to attack-the-premise and then to the user. The skill is hidden from the model and bundles the script that sets the Status of a ticket.
- f4a5802: Add the issue skill. It runs the templates skill for the issue forms, picks the bug, feature, refactor, chore or epic form, creates the labels they set and interviews the user with grilling, installed globally when it is missing, when the request leaves a field open. It opens the form prefilled in the browser through a URL that a bundled script builds and checks against GitHub's length limit. When another skill asks for the issue, it creates it with `gh` after the user confirms the draft. It decides the project fields such as priority and size, splits an epic into a parent and sub-issues, shows a changed flow or structure as a diagram, sets one `app: <name>` label per application in a repository with several, and attaches the interview as the first comment. Every issue is written in English.
- 745785d: Add the package-manager skill, one table that maps the lockfile of a repository to its install, add and run commands. The commit and issue skills read it.
- f6aaeb3: Add the project-docs skill for Markdown documentation with one question per file, fixed forms such as Tutorial, links instead of retelling and a markdownlint configuration. Every sentence follows technical-writing, and a diagram of one flow or feature goes in the README of its folder. A PostToolUse hook checks documentation files for long dashes, semicolons, dead relative links, a missing opening sentence and files the README does not link, and reports what markdownlint finds.
- 8ed6cae: Add the project skill. It gives an owner a GitHub Project with the Status, Priority and Size fields the issue skill sets, by creating one or extending a chosen project. A bundled script applies the field set, keeps the values of the items and drops an option beyond the set only when told. Size XL is a full day of work. The skill links the project to the repository and lists the workflows and views that stay manual. It is hidden from the model, and the issue skill reads it by path when the owner has no project or the chosen one lacks the fields.
- ddfc141: Add the pull-request and pull-request-review skills. Every pull request opens as a draft from the template of the templates skill, with Summary, Diagram, Linked issue, Scope, Tradeoffs, Blast radius, Automated coverage and a test plan of numbered steps that the reviewer runs in the application, with prerequisites for iOS, web, API and CLI. The body follows technical-writing and stays under about 40 lines apart from the test plan. The skill finds the issue in the prompt, the branch name and the commit trailers, brings the diagrams a branch touches up to date and lists every decision it took as an assumption. The draft turns ready for review itself when every check passes, the test steps the agent can run pass, no assumption is open and nothing waits for the user. The ci-watcher agent waits for the checks, and loop-on-ci fixes a failed one. Otherwise the draft stays until the user calls it ready, and marking it ready requests the named reviewer and sets the issue to In review. pull-request-review checks out a pull request, starts the application through a `verify-<app>` skill when the repository holds one, runs the steps it can drive, hands the rest to the reviewer and posts the result with a row per step and the evidence of its own steps. A bundled script ticks the passed steps in the description. The approval stays the reviewer's own click, and pull-request-review is hidden from the model.
- 09c73d3: Add a SessionStart hook that hands Claude the session id, the transcript path and the plugin root, and tells it to read a skill of this plugin from `<root>/skills/<category>/<name>/SKILL.md` instead of calling the Skill tool.
- 975fd35: Add the templates skill, which owns the issue forms and the pull request template of a repository and keeps them up to date without asking. The templates come from the skill's assets, with only the `contact_links` of `config.yml` and the prerequisites of the pull request template taken from the repository. It writes every template that is missing, overwrites every one that differs, whoever wrote it, and leaves other files in `.github/ISSUE_TEMPLATE/` alone. Each asset starts with a marker line that says the file is overwritten. Each kind is its own commit, on the branch `chore/templates` when the default branch or `dev` is checked out. The skill is hidden from the model and starts through `/templates` or when the issue or pull-request skill reads it by path.
- 2c25173: Add the today-issues skill. It reads the open tickets of a GitHub Project through a bundled script, with Status, Priority, Size, labels, epic, open blockers and open pull requests, from every repository the project holds, and keeps the tickets assigned to the user or to nobody. It asks for three budgets, total run time, time for questions and time for reviews, estimates each ticket from its Size and its body, and ranks reviews first, then Critical, work in progress, a begun epic, the build order of an application, the remaining priorities and short tickets. It groups the tickets into tracks that run side by side when they touch different repositories or applications, read from the repository of each ticket and from its `app: <name>` labels. An epic runs alone, and a ticket waits for the merge of its blocker. The plan is one table per track with the ticket, run, questions, review and reason, the sums against the budgets, what stays out and what the tickets lack. The skill only reads, and it is hidden from the model.
- 549852f: Adopt skills of pstack and Cursor Team Kit from cursor/plugins word for word, adapted to Claude Code through the mapping in UPSTREAM.md. The 24 principles of pstack live under `skills/principles/`, each named `principle-<slug>`. The workflow category holds how, why, architect, arena, interrogate, swarm, blast-radius, figure-it-out, tdd and show-me-your-work. The verification category holds control-ui, control-cli and verify-this from Cursor Team Kit, create-verification-skill, maintain-verification-skill and benchmark-checklist. The meta category holds reflect, correct, recall, automate-me, teach, bro and setup-models, which writes the model and the effort of each role to `~/.claude/rules/models.md`. The github category holds loop-on-ci from Cursor Team Kit, the ci-watcher agent watches the checks of a pull request, the docs category holds unslop and technical-writing, and the clean-code category holds typescript-best-practices. `pnpm run check-upstream` lists, for every copied file, the upstream commits since the base commit that touched it and prints their diff.

### Minor Changes

- 33b09a1: Adopt the pstack guide under `docs/guide/`, adapted to this plugin through the mapping in UPSTREAM.md, with an own page on working a GitHub issue to a draft pull request.

### Patch Changes

- 97b1f0c: Every Codex entry in `~/.claude/rules/models.md` names its model and its effort, such as `codex:astra/xhigh`. The Codex models are `luna`, `sol` and `astra`, and the engineering skill's `codex-model.mts` resolves each to the newest full name the Codex CLI lists, such as `gpt-6-astra`.
  
  A Codex slot no longer starts when the account reached its usage limit or has less of its 5-hour or weekly window left than the `codex minimum` line sets, which `/setup-models` asks for and which defaults to 20 %, unless credits pay for the run. A Codex slot that cannot run falls back to the Claude model of the same rank, `haiku` for `luna`, `sonnet` for `sol`, and `opus` for `astra`, instead of always to `sonnet`.
