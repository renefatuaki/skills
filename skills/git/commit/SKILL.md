Rules for every commit you create. A commit is one topic with a message that follows Conventional Commits and references the GitHub issue when there is one, so the history stays reviewable and every change links back to its discussion. Git enforces the message through commitlint in a husky `commit-msg` hook. The message and its validation follow two upstream skills, this skill covers what they leave open: enforcement and the skills being present, the issue, the split, the plan.

## Steps

1. **Ensure enforcement.** Look for a commitlint configuration (`commitlint.config.*`, `.commitlintrc*`, or a `commitlint` key in `package.json`) and a `commit-msg` hook that runs it (`.husky/commit-msg`, or a `commit-msg` command in `lefthook.yml`). Both present: continue. Missing and the repository has a `package.json`: follow commitlint's [Getting started](https://commitlint.js.org/guides/getting-started.md) and [Local setup](https://commitlint.js.org/guides/local-setup.md) guides with the repository's package manager (read from its lockfile, pnpm when there is none), then replace the generated configuration with a copy of [assets/.commitlintrc.yaml](assets/.commitlintrc.yaml). It extends `@commitlint/config-conventional` and adds `references-empty` as a warning, so a commit without an issue reference passes with a note. Commit the setup on its own as `build: add commitlint and husky`. No `package.json`: ask whether to create one, otherwise follow the rules below by hand and say so in your reply. Never install anything without confirmation.
2. **Ensure the upstream skills.** Look for `conventional-commit-message` and `committing-with-commitlint` under `.claude/skills/` of the repository or of the user. Missing: install them after confirmation.

   ```sh
   pnpx skills add https://github.com/conventional-changelog/conventional-changelog --skill conventional-commit-message
   pnpx skills add https://github.com/conventional-changelog/commitlint --skill committing-with-commitlint
   ```

   No network access: say so and follow the [Conventional Commits 1.0.0 specification](https://www.conventionalcommits.org/en/v1.0.0/) directly.
3. **Read the stage.** Run `git status --porcelain`, `git diff --cached` and `git log --oneline -20`. Only staged changes are in scope. Nothing staged: list the unstaged files and stop. Never run `git add -A` or `git add .` unless asked. Adopt the language of the existing log.
4. **Find the issue.** Look in the prompt, the branch name, the open pull request of the branch (`gh pr view --json number,body`), then an issue linked there. Nothing found: ask whether to create an issue from the diff (`gh issue create`) or to commit without one. Commit without a reference only when the user says the work has no issue, never silently. GitHub links `#123` anywhere in the message ([autolinked references](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/autolinked-references-and-urls)), and closing keywords close the issue once the commit reaches the default branch ([linking a pull request to an issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)). Write `Refs: #123` for a reference, `Closes #123` when the commit finishes the issue. GitHub treats `Fixes` and `Resolves` the same, keep the one the log already uses.
5. **Group by topic.** The specification's [FAQ](https://www.conventionalcommits.org/en/v1.0.0/#faq) answers a commit that would need more than one type with "go back and make multiple commits whenever possible", and the upstream skill asks for one commit per coherent change. Split the stage along those lines before writing any message. Stage each group by applying patches to the index (`git apply --cached`), never with the interactive `git add -p`, and never overwrite the working file, so unstaged changes of the user survive.
6. **Write each message** with the `conventional-commit-message` skill: the type by release impact, the scope from the repository, a changelog-ready description, footers as trailers. Add the issue as a footer. The person running the session is the author: no `Co-Authored-By` or "Generated with" line naming an AI, no session link.
7. **Validate** with the `committing-with-commitlint` skill: read the resolved rules, pipe the complete message through commitlint before committing, and fix only the rules named in brackets. A warning from `references-empty` is expected when the user chose to commit without an issue.
8. **Present the plan.** A table with one row per commit: number, files, subject. Wait for the user to confirm. Exactly one commit and no open question: commit directly. No user who can answer: print the plan and continue.
9. **Commit.** Per group `git add` the files, then `git commit -F -` with a quoted heredoc so quotes in the body survive. commitlint runs in the `commit-msg` hook and prints the broken rules on rejection: fix the message and commit again. Never `--no-verify`, never `HUSKY=0`, never `--amend` unless asked. Afterwards show `git log --oneline -n <count>`.

Done when the stage is empty and every new commit passed commitlint.
